# Living Glossary — Architecture Spec
# Status: PLANNED — not yet built
# Depends on: visual-composition-orchestrator (Section 1 Analysis Mode)

---

## What It Is

A structured, version-controlled glossary that grows automatically as new images
are analyzed by the visual-composition-orchestrator. Every word bank extracted
during Analysis Mode is written into the glossary — deduplicated, categorized,
and tagged with its source image. The glossary is queryable, exportable, and
usable by downstream skills (curriculum-architect, content-generator, ux-instructional-design).

It is NOT a database. It is a set of structured YAML files that Claude reads and
writes directly. Simple, inspectable, no infrastructure required.

## Where It Lives

```
visual-composition-orchestrator/
└── glossary/
    ├── glossary-index.yaml       # master index of all terms + metadata
    ├── domains/
    │   ├── landforms.yaml        # terms extracted from landform images
    │   ├── biomes.yaml           # terms extracted from biome images
    │   ├── bloom-taxonomy.yaml   # Bloom verb lists
    │   ├── flags.yaml            # country/flag terms
    │   └── [domain].yaml         # auto-created when new domain detected
    └── GLOSSARY-README.md        # explains the format to Claude and humans
```

## Glossary Entry Format

Each term in a domain file follows this schema:

```yaml
- term: "Delta"
  definition: "A landform at the mouth of a river where sediment is deposited"
  domain: "landforms"
  subdomain: "water_features"
  source_image: "climatelandforms.png"
  source_zip: "Test_Images.zip"
  date_added: "2026-04-14"
  confidence: HIGH        # HIGH / MEDIUM / LOW — from visual analysis rubric
  cross_references:
    - River
    - Estuary
    - Sediment
  bloom_level: null       # filled if term is a Bloom verb
  tags: ["geography", "water", "landform"]
```

---

## Glossary Index Format

`glossary-index.yaml` is a flat lookup table — term → domain, for fast cross-domain search.

```yaml
index:
  - term: "Delta"
    domain: "landforms"
    subdomain: "water_features"
  - term: "Analyzing"
    domain: "bloom-taxonomy"
    subdomain: "ANALYZING"
  - term: "Taiga"
    domain: "biomes"
    subdomain: "biome_types"
```

## How It Gets Populated — The Write Protocol

This is the mechanism that makes it "living." The write protocol runs at the END
of every Section 1 Analysis Mode pass that successfully extracts a word bank.

### Step 1 — Domain detection
After extracting a word bank, classify it into a domain:
- Landform terms → `landforms`
- Biome names → `biomes`
- Bloom taxonomy verbs → `bloom-taxonomy`
- Flag/country names → `flags`
- Unclassified terms → `[auto-generated domain name based on image filename stem]`

### Step 2 — Deduplication check
Before writing any term, check `glossary-index.yaml`:
- If the term already exists in the same domain → skip (no duplicate)
- If the term exists in a DIFFERENT domain → write to new domain AND add
  `cross_domain: true` flag to both entries
- If the term is new → write to domain file + add to index

### Step 3 — Write to domain file
Append new entries to the appropriate `domains/[domain].yaml`.
If the domain file doesn't exist, create it with a header block:

```yaml
# [domain] glossary
# Auto-generated by visual-composition-orchestrator Ingest Mode
# First populated: [date]
# Source: [image filename]

terms:
```

### Step 4 — Update the index
Append new entries to `glossary-index.yaml`. Maintain alphabetical sort.

### Step 5 — Report to user
After writing, report:
```
Glossary updated:
  [N] new terms added to [domain]
  [N] duplicates skipped
  [N] cross-domain flags set
  Total glossary size: [N] terms across [N] domains
```

## How Downstream Skills Use the Glossary

### curriculum-architect
Reads `glossary/domains/[domain].yaml` when building a module on that topic.
Uses the term list as the word bank for lesson vocabulary.
Cross-references subdomain structure to sequence terms by complexity.

### content-generator
Reads glossary entries to ensure generated problems use confirmed terminology.
Uses definitions for auto-generating definition-matching question types.

### ux-instructional-design
Reads glossary for word bank drag-drop exercises, labeling activities,
and fill-in-the-blank interactions. Term confidence levels map to
scaffolding depth (LOW confidence terms get worked examples first).

### visual-composition-orchestrator (self-referential)
On each new analysis pass, checks the glossary before extracting a word bank.
If the domain already exists, it extends rather than rebuilds from scratch.

## Build Requirements

To build the living glossary as a skill component:

1. **Script:** `scripts/write_glossary.py`
   - Args: `--terms [yaml list]`, `--domain [str]`, `--source [filename]`, `--glossary-dir [path]`
   - Handles deduplication, index update, domain file creation, cross-domain flagging
   - Outputs a write report (terms added / skipped / flagged)

2. **Reference file:** `glossary/GLOSSARY-README.md`
   - Explains schema to Claude on load
   - Lists all active domains
   - States the write protocol (Step 1–5 above)

3. **Update to SKILL.md:** Add Step 5 to Section 1 (Analysis Mode)
   - After extracting word bank → run write_glossary.py
   - Report glossary update to user before routing downstream

4. **Update to manifest-format.md:**
   - Add glossary_domains_affected field to manifest output
   - Tells Claude which domain files will be written during analysis

---

## What's NOT in This Build

- No database, no API, no external storage
- No user-facing UI (glossary is a backend artifact — downstream skills surface it)
- No automatic definition generation (definitions come from images or are flagged as needing manual entry)
- No automatic translation or synonym mapping (future extension)
